# OreSight — Full System Architecture

**Hackathon:** Smart India Hackathon 2026
**Problem domain:** Manganese mine reserve intelligence and production decision support
**Mine:** DEMO-01 (Balaghat-type synthetic dataset, seed 42)

---

## The Problem OreSight Solves

A manganese mine has a geological survey that says it holds millions of tonnes of ore. But that number is misleading — it says nothing about how much you can actually mine today, whether you'll hit your monthly target, or what you should do if you're falling behind.

OreSight bridges that gap. It answers four questions in sequence:

1. **What ore actually exists?** → PRISM (Geological Reserve)
2. **How much of it can we mine right now?** → EAR (Accessible Reserve)
3. **Will we hit our production target?** → PULSE (Forecast + Risk)
4. **What one action moves the needle most?** → NUDGE (Recommendation)

## Layer 2 — ML Pipeline

The pipeline is a **linear chain of five offline Python scripts**. Each stage reads from `data/raw/` and/or the outputs of prior stages, then writes to `models/output/`.

> The pipeline runs once (or when data changes). The backend never re-runs it.

---

### Stage 1 — PRISM: Geological Reserve Estimation

**Script:** `models/prism.py`
**Question answered:** *Where is the ore, and how much tonnage does it represent?*

PRISM takes sparse borehole samples and estimates Mn (manganese) grade at every point in the mine's 3D block model using **Ordinary Kriging** — the industry-standard geostatistical interpolation technique.

**How it works:**

```
Borehole composites (sparse, known grades)
         │
         ▼
Experimental variogram fitted by grid search
(spherical model: nugget / partial sill / range)
         │  Z-anisotropy ×5 applied
         │  (vertical correlation is shorter than horizontal)
         ▼
Local Ordinary Kriging — 20 nearest neighbours per block
Solves: [γ matrix | 1] × [weights | λ] = [γ(h) | 1]
         │
         ▼
Per-block estimated Mn% + kriging variance (uncertainty)
         │
         ▼  Mn ≥ 20% cutoff
Classification: ore (498 blocks) vs waste (1,742 blocks)
         │
         ▼
Tonnage = volume_m³ × density × ore_flag
```

**Outputs:**

| File | Contents |
|---|---|
| `reserve_blocks.csv` | 2,240 blocks with estimated_mn_pct, kriging_variance, tonnage_t, is_ore |
| `reserve_summary.json` | Declared reserve: 48.27 Mt, avg Mn: 25.2%, variogram parameters |

**Key numbers:** 2,240 total blocks → 498 ore blocks → **48.27 Mt declared reserve**

---

### Stage 2 — EAR: Effective Accessible Reserve

**Script:** `models/ear.py`
**Question answered:** *How much of that ore can we actually mine under today's operational constraints?*

EAR is the bridge between geology and operations. It filters PRISM's ore blocks through three real-world constraints. A block must pass **all three** to be counted as accessible.

**Three constraints:**

```
PRISM ore blocks (498 blocks, 48.27 Mt)
         │
         ├── Constraint 1: Development Readiness
         │     Block elevation z ≤ 192 m
         │     (proxy for tunnel/drift access depth)
         │     Removes ~25% of ore blocks
         │
         ├── Constraint 2: Equipment Availability
         │     Mine-wide mean fleet availability ≥ 85%
         │     (mine-wide boolean check across all equipment)
         │     Fleet mean = 90.6% → constraint PASSES
         │
         └── Constraint 3: Weather Feasibility
               Rainfall ≤ 30 mm/day (monsoon threshold)
               94.3% of days meet this threshold
               Applied probabilistically per block (seed 42)
         │
         ▼
         Accessible blocks: 339 of 498
         Inaccessible blocks: 159 (development + weather blocked)
```

**Decision rule:**
```
accessible_tonnage = declared_tonnage  IF (dev_ready AND equip_available AND weather_feasible)
                   = 0                 OTHERWISE
```

**Outputs:**

| File | Contents |
|---|---|
| `ear_blocks.csv` | 498 ore blocks with development_ready, equipment_available, weather_feasible, accessible_tonnage_t |
| `ear_summary.json` | EAR: 32.74 Mt, accessibility ratio: 67.8%, per-constraint breakdown |

**Key numbers:** 48.27 Mt declared → **32.74 Mt accessible** (67.8% accessibility ratio)

### Stage 3 — PULSE: Production Forecasting

**Script:** `models/pulse.py`
**Question answered:** *Will we hit our planned production target over the next 30 days?*

PULSE uses **LightGBM quantile regression** to forecast daily production with three uncertainty bands (P10/P50/P90) and derives a shortfall probability.

**Feature engineering (~38 features):**

```
Historical data → Feature matrix
│
├── Lag features: actual_t shifted 1, 2, 3, 7, 14, 30 days back
├── Rolling stats: 7/14/30-day mean & std of production and fleet availability
├── Rolling rainfall sum: 7-day window
├── Operational: fleet_availability, fleet_downtime_h, blast_count, delay_h,
│               development_m, available_workers, shifts
├── Weather: rainfall_mm, soil_moisture, NDVI, LST
└── Temporal: day_of_week, month, quarter, day_of_year
```

> All features use only past data — no lookahead, no data leakage.

**Chronological split (no random shuffle):**

```
2023-01-31 ──────────── 2025-10-02 ──── 2025-12-01 ── 2025-12-31
│         Training (976 days)        │  Validation  │  Forecast  │
│                                    │  (60 days)   │  (30 days) │
```

**Three quantile models trained in parallel:**

```
Training data
    │
    ├── LightGBM α=0.10 → P10 model (pessimistic bound)
    ├── LightGBM α=0.50 → P50 model (expected / median)
    └── LightGBM α=0.90 → P90 model (optimistic bound)
    │
    ▼
30-day daily forecast: [p10_t, p50_t, p90_t] per day
    │
    ▼
EAR cap: if cumulative P50 > accessible reserve → scale all quantiles down
(not binding here: 68,593 t ≪ 32.74 Mt)
    │
    ▼
Shortfall probability per day (linear interpolation between quantiles)
```

**Outputs:**

| File | Contents |
|---|---|
| `pulse_forecast.csv` | 30 rows: date, planned_t, p10, p50, p90, shortfall_t, shortfall_probability |
| `pulse_summary.json` | Planned: 71,989 t, P50: 68,593 t, shortfall: 3,396 t, shortfall_prob: 88.4% |

**Validation metrics (P50 on held-out data):** MAE 61.3 t/day, RMSE 77.4 t/day, MAPE 2.66%

**Key numbers:** 88.4% probability of missing the 30-day target. Expected shortfall: **3,396 tonnes (4.7% below plan)**.

PULSE also exposes `run_pulse_with_models()` which returns the trained LightGBM boosters. The next two stages reuse these models without retraining.

---

### Stage 4 — RISK + SHAP: Risk Classification and Root-Cause Attribution

**Script:** `models/risk_shap.py`
**Question answered:** *How severe is the risk, and which operational factors are driving it?*

This stage splits into two parts that run together:

#### RISK — Classification

Reads `overall_shortfall_probability` from `pulse_summary.json` and applies a transparent threshold rule:

| Level | Shortfall probability |
|---|---|
| LOW | < 25% |
| MEDIUM | 25% – < 50% |
| HIGH | 50% – < 75% |
| **CRITICAL** | **≥ 75%** |

88.4% → **CRITICAL**. No new model is built.

#### SHAP — Feature Attribution

Runs `shap.TreeExplainer` on the live P50 LightGBM model from PULSE. SHAP (SHapley Additive exPlanations) decomposes each prediction into per-feature contributions — it shows how much each feature pushed the forecast up or down relative to the average prediction.

```
P50 LightGBM model (from run_pulse_with_models)
    │
    ▼
shap.TreeExplainer (tree_path_dependent, check_additivity=False)
    │  Background: 200 random training rows (seed 42)
    ▼
SHAP values for all 38 features × all training rows
    │
    ▼
mean(|SHAP|) per feature → importance ranking
    │
    ▼
Label each feature:
  ACTIONABLE — mine can control this (fleet, blast, development, manpower)
  CONTEXTUAL — outside operational control (weather, calendar)
```

**Top 5 drivers:**

| Rank | Feature | Mean \|SHAP\| | Direction | Type |
|---|---|---|---|---|
| 1 | planned_t | 97.16 | DOWN | ACTIONABLE |
| 2 | rainfall_mm | 41.93 | DOWN | CONTEXTUAL |
| 3 | fleet_availability | 24.24 | DOWN | ACTIONABLE |
| 4 | development_m | 17.55 | DOWN | ACTIONABLE |
| 5 | delay_h | 16.98 | DOWN | ACTIONABLE |

**Outputs:**

| File | Contents |
|---|---|
| `risk_summary.json` | Risk level: CRITICAL, shortfall metrics, top/actionable/contextual drivers |
| `shap_importance.csv` | 38 features ranked by mean \|SHAP\|, impact_direction, driver_type |

### Stage 5 — NUDGE: Prescriptive Recommendation

**Script:** `models/nudge.py`
**Question answered:** *What single action should the mine manager take right now?*

NUDGE takes the ACTIONABLE features from SHAP and finds the one intervention that produces the greatest measurable reduction in the expected 30-day shortfall — using the PULSE model itself as the response surface. No new model is trained.

**Four intervention levers (controllable only):**

| Feature | Intervention | Bound (from historical data) |
|---|---|---|
| `fleet_availability` | Preventive maintenance scheduling | ≤ p95 = 0.957 |
| `fleet_downtime_h` | Reduce unplanned stoppages | ≥ p10 = 10.54 h |
| `development_m` | Increase development advance | ≤ p90 = 19.59 m/day |
| `available_workers` | Mobilise standby workforce | ≤ max = 92 persons |

**Excluded levers:** `planned_t` (external input), `delay_h` (already 0 in forecast), `shifts` (already at max 3).

**Counterfactual scoring process:**

```
For each lever × each candidate value (4–6 levels between baseline and bound):
    │
    ├── Copy the 30-day forecast feature matrix
    ├── Replace that one feature column with the candidate value (all rows)
    ├── Run PULSE P50 LightGBM → get mean daily production prediction
    ├── Compute 30-day total production gain and shortfall reduction
    └── Check EAR constraint: 30-day total ≤ accessible reserve
    │
    ▼
All feasible candidates ranked by shortfall_reduction_t
    │
    ▼
PuLP CBC binary integer program: select exactly 1 action, maximise shortfall_reduction_t
    │
    ▼
Re-estimate new shortfall probability with P10/P50/P90 models under chosen counterfactual
```

**Result:**

| # | Action | Recommended value | Production gain | Shortfall reduction |
|---|---|---|---|---|
| **1** | **Increase development progress** | **18.53 → 19.24 m/day** | **+606.6 t** | **-606.6 t** |
| 2 | Improve fleet availability | 0.906 → 0.957 | +415.2 t | -415.2 t |
| 3 | Reduce equipment downtime | → 10.54 h | +163.5 t | -163.5 t |
| 4 | Increase available workforce | → 90.97 persons | +30.1 t | -30.1 t |

New shortfall probability under best action: **88.0%** (from 88.4%). Expected shortfall: **2,789 t** (from 3,396 t).

**Outputs:**

| File | Contents |
|---|---|
| `nudge_recommendation.json` | Best action, baseline, new shortfall metrics, constraints, assumptions |
| `nudge_candidates.csv` | All evaluated candidates ranked by shortfall_reduction_t |

## Layer 4 — FastAPI Backend

**Location:** `backend/main.py`
**Framework:** FastAPI 0.100+ / Uvicorn / Pydantic v2
**Start:** `uvicorn backend.main:app --reload` → `http://127.0.0.1:8000`

The backend is a **pure read-only presentation layer**. It reads the 10 precomputed files and serves typed JSON. Zero model logic runs here.

**Design principles:**
- Missing output file → clean HTTP 404 (not a 500 traceback)
- Malformed file → clean HTTP 500 with a clear message
- NaN / Infinity floats → replaced with `null` before serialisation
- CORS open for `localhost:3000` and `localhost:5173`

## Key Design Decisions

**Why offline pipeline, not live inference?**
Hackathon MVP constraint. Kriging and LightGBM training take seconds on a laptop. Precomputing outputs means the backend is instant (just file I/O) and the frontend always has data even if the pipeline hasn't re-run.

**Why no model serialisation (.pkl files)?**
PRISM, PULSE, RISK+SHAP, and NUDGE are all run sequentially in one pipeline session. NUDGE and RISK+SHAP reuse the PULSE models via `run_pulse_with_models()` — an in-memory pass. Persisting the model is unnecessary for the current architecture.

**Why flat files instead of a database?**
No PostgreSQL/SQLite needed at this scale. 10 output files totalling a few MB. FastAPI reads them on each request (with negligible overhead). Keeps the stack simple and dependency-free.

**Why three separate quantile LightGBM models?**
Quantile regression requires training a separate model per quantile. Each model minimises its respective pinball loss. Running P10/P50/P90 as three independent models is the standard approach and avoids quantile crossing at the model level (monotonicity is enforced post-prediction).

**Why PuLP in NUDGE?**
Provides a formal, auditable decision record. It is a trivial binary integer program (select exactly 1 of N candidates) but frames NUDGE as an optimization problem — extensible to multi-action selection or budget-constrained portfolios without rearchitecting.

**Why lazy-load Plotly?**
Plotly.js is ~3 MB. Lazy-loading it with a dynamic `import()` keeps the initial React bundle small. The 3D views load Plotly only when the user navigates to PRISM or EAR.
